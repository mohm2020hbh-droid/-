# Pogostuck_Physics_Implementation_Report.md

Implementation of **`Pogostuck_Physics_LOCKED_SPEC.md`** (the only source used) in the Android project `pogo-summit/game`.
Scope of the claim: the **locked equations E1–E18 and the locked constants** are implemented as written. The original's collision engine is **not** restored (spec §7, class D) — it is our own implementation, described below.

Verdict: **all executable validation targets pass** (see §5); **no value was edited to make a test pass**. Differences that remain are listed in §7 and §8.

---

## 1. What was applied

- A new **Physics Core** under `game/src/sim/` (pure TypeScript, no DOM/Three.js/clock/RNG — enforced by `tests/architecture.test.ts`), separated from Rendering (`src/render`), Input (`src/input`) and UI (`src/ui`).
- Fixed **120 Hz** loop, **Δt = 16·(973/1024)/120 = 0.126693 T** per tick (spec §2); float64 state in the spec's units (Q, T, L, degrees). Presentation values (metres at 52 Q = 1 m, m/s, rad) are derived from the state each tick and are read only by the renderers/HUD.
- Physics Core modules in the order requested (`src/sim/core/`), executed in the spec's own pipeline order (§3), orchestrated by `core/step.ts`:

## 7. Remaining differences from the LOCKED SPEC

1. **Passive-bounce figures (§10 "Passive bounce") differ by up to 1.4 %.** The spec's 40.28 / 29.69 are analytic (L = exactly 40.0 / L_min). The literal E8 charges in whole ticks of 16·Δt = 2.027 L, so the first load ≥ 40 is 40.542 (20 charge ticks), giving 30.096 Q/T. The first landing's L_min (53.585 vs 54.26) differs because E7 uses the velocity of the tick on which `g` turns 1: measured |v| = 69.47 Q/T (I = 83.40) instead of the analytic 70.52 (I = 84.57). The E6 probe reaches 6 Q beyond the tip, so ground is detected slightly before the tip touches it (v² = 70.52² − 2·8.5·6 → ≈ 69.8), plus whole-tick sampling. I implemented E7/E8 as written and did not alter any value to match the analytic numbers; the tests assert the measured chain with explicit bounds (e.g. idle hop 29.6–30.6).
2. **Launch tick = charge ticks + 1** (the launch happens on the first grounded tick where the charge condition fails). Spec text does not state tick counting; recorded here so it is not mistaken for a spec figure.
3. **Collision engine is ours (class D).** Details: tip circle r = 4 Q + an oriented hull box (±12.5 Q across, z_min…+30 Q along the stick); floor-like contacts of the hull's lower end are ignored in the position resolution because the tip supports the body (`hullSupportsFloor = 0`), but every hull contact blocks rotation (hull bottom lifted 16 Q); sub-stepped movement (2 Q); the ground probe is a swept ±4 Q circle with bisection; the E14 reflection direction `r̂` is computed from the reflected displacement (the spec's fallback `v − 2(v·n)n` exists, the engine's `bounce` vector does not); moving-platform velocity `c` comes from the platform's per-tick displacement. These are the pieces the spec says Android must supply; they are **not** a restoration of the original engine.
4. **Gameplay mechanics that no longer exist** because the spec has none: boost button (the button/counter remain visible in the HUD but are inert; boost is the automatic E13 spin), pull-power gesture and charge-time setting (inert settings), coyote time/press buffer, restitution/spring parameters. The bounce pad `pad1` is now an ordinary surface (entity bounce pads are excluded by spec §8).
5. **The pogo hops continuously by itself** (idle bounce is inherent in E8: L < L_min charges without input, then launches). The `jumps` counter therefore counts idle hops (the recorded route has 38 jumps).
6. **Respawn rule (DESIGN):** the safe-respawn point is recorded at landing (`safeLandingRecord`); this is not part of the spec.
7. **`hardImpactLoad = 150`** (DESIGN): used only for the hard-impact event/VFX intensity; it does not feed back into the physics.
8. **LEVEL_01 geometry unchanged**, as required (no gameplay-design change). With the locked physics the level is **solvable** (goal reachable; every platform reachable; the route bot finds a full run: 36 plans, 38 jumps, 6056 ticks = 50.5 s of simulation, par 80 s), but two hops are **tight**: with the conservative window L ∈ [40, 95] (brute-force grid of 348 cells per start point) `q1→q2` has 2 landing cells and `q2→q3` has 4, launched from platform edges (the analysis now includes edge start points 2 % / 98 %). Other hops: 8–62 cells. Decision for a later task: widen those two gaps in level data (a design change), not the physics.
9. **Reachability analysis is conservative**: every standing node is assumed to have the v = 0 landing window. A real landing with higher speed opens a wider window (E7), so real play has at least this freedom; the route bot proves an end-to-end run on the real physics.
10. **Numeric precision:** float64, not 22.10 fixed point (spec §9: allowed, ≤ ~1/1024 per stored quantity per frame).
11. **`PHYSICS_UNCERTAINTIES.md` / `PHYSICS_ANALYSIS.md`** describe the earlier model and were not rewritten in this task; the authoritative documents are the LOCKED SPEC, `PHYSICS_MASTER.md` and this report.
